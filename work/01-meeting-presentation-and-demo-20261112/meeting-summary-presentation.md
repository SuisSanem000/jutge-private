## Slide 5: The Pedagogical Constitution (`spec/constitucio.md`)
- **Strict Efficiency Standards:**
  - No unnecessary computation; loops must terminate immediately when a search succeeds.
  - Worst-case time complexity must be strictly separated from naive approaches.
- **C++17 Restricted Subset (Pedagogical Guardrails):**
  - **Forbidden Features:** No `std::unordered_map`, no lambdas, no `enum class`, no `constexpr`, no `std::string_view`, no `std::variant`, no structured binding, no exceptions.
  - **Allowed Features:** Strict standard I/O (`<iostream>`), basic STL (`<vector>`, `<string>`, `<algorithm>`, `<queue>`, `<stack>`), and `auto` restricted to iterators.
- **Pedagogical Integrity:**
  - Problems must test algorithmic insight, not esoteric language trivia.

## Slide 11: Algorithmic Problem Design: "Dominant Mountain Peaks"
- **Problem Statement Concept:**
  - Given a sequence of integer elevations, a peak is "dominant" if it is strictly higher than all peaks that appear after it to its right.
- **Input / Output Specification:**
  - Reads test cases until EOF; each test begins with $n$ followed by $n$ integers.
  - Outputs dominant peaks in their original order.
- **Example:**
  - Input: `1 4 2 3 5` $\rightarrow$ Output: `5`
  - Input: `3 1 4 1 2 1` $\rightarrow$ Output: `4 2 1`
  - Input: `9 7 4 -2` $\rightarrow$ Output: `9 7 4 -2`

---

## Slide 12: Dual Algorithm Implementations
- **Golden Solution (`solution.cc`):**
  - **Time Complexity:** $O(n)$ linear time.
  - **Space Complexity:** $O(n)$ auxiliary space to store the sequence and collect results.
  - **Algorithm:** Reads elements into a vector, scans from right to left tracking the running maximum, collects dominant peaks, and prints them in forward order.
- **Slow Solution (`solution-slow.cc`):**
  - **Time Complexity:** $O(n^2)$ quadratic worst-case.
  - **Algorithm:** For every peak, runs an inner search loop scanning all subsequent elements.
  - **Early Termination:** Stops immediately when a peak $\ge$ current is found (satisfying the constitution).

---

## Slide 13: Edge-Case Engineering & Vectorization Defeat
- **The Compiler Optimization Challenge:**
  - Claude's initial naive solution was vectorized by `g++ -O2`, running in 1.1s vs 0.34s (only a $3.2\times$ difference, failing the $5\times$ guideline).
- **The Architectural Fix:**
  - Claude restructured `solution-slow.cc` to break at the first higher peak.
  - Identified that strictly **decreasing** sequences trigger worst-case quadratic comparisons ($O(n^2)$ full scans).
- **Test Generation (`generate.ts`):**
  - Generates 2 strictly increasing and 3 strictly decreasing sequences of 100,000 elements.
  - Output exceeds default 2 MB limits, so `generate.ts` automatically writes `private-efficiency-2-monotone.ops` with `--maxoutput=4`.

## Slide 22: Web Service Ingestion Protocol (`lib/upload.ts`)
- **Step 1: Filtering & Zipping:**
  - Scans directory, excludes temporary artifacts (`.o`, `.exe`, `.bak`, `__pycache__`, `.DS_Store`).
  - Bundles problem files into `.jtk-zip/<id>/<problem>.zip`.
- **Step 2: API Request:**
  - Sends HTTP POST `multipart/form-data` to `https://api.jutge.org/api` with function `instructor.problems.create`.
- **Step 3: WebStream Real-Time Feedback:**
  - Listens to Server-Sent Event stream at `/api/webstreams/<stream-id>`, printing server compilation and lint logs in real time.
- **Step 4: ID Assignment & `problem.yml` Creation:**
  - Regex captures `Problem ([A-Z]\d{5}) created.`
  - Saves Problem ID and metadata into `problem.yml`.

## Slide 26: Architectural Proposal: Phase 3 `@jutge/core`
- **The Core Problem:**
  - `jtk` is currently a monolithic CLI where business logic is trapped inside terminal UI handlers.
- **The Solution: Decoupled 3-Layer Architecture:**
  - **Layer 1: `@jutge/core` (Headless Engine):**
    - Pure TypeScript SDK. Compiles, lints, generates tests, and uploads via pure API calls with zero terminal dependencies.
  - **Layer 2: `@jutge/cli` (`jtk v5`):**
    - Thin CLI wrapper over `@jutge/core` using Commander.js for terminal users.
  - **Layer 3: `@jutge/service` (API & Web SaaS):**
    - Exposes `@jutge/core` via REST / MCP (Model Context Protocol) to serve the Web Problem Editor and AI agents.

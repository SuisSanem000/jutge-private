## Slide 5: The Pedagogical Constitution (`spec/constitucio.md`)
- **Strict Efficiency Standards:**
  - No unnecessary computation; loops must terminate immediately when a search succeeds.
  - Worst-case time complexity must be strictly separated from naive approaches.
- **Restricted C++17 Subset:**
  - **Allowed:** Standard I/O (`<iostream>`), basic STL (`<vector>`, `<string>`, `<queue>`, `<stack>`, `<algorithm>`).
  - **Restricted auto:** Allowed only for iterators and clear return types.
  - **Forbidden:** No `std::unordered_map` (prevents hash collisions / non-deterministic orders).
  - **Forbidden:** No lambdas, enum class, constexpr, string_view, variant, structured bindings, or exceptions.
- **Pedagogical Integrity:**
  - Problems must test algorithmic insight, not language trivia.

## Slide 11: Algorithmic Problem Design: "Dominant Mountain Peaks"
- **Concept:**
  - A mountain peak is dominant if strictly higher than all peaks appearing to its right.
- **Input / Output Specification:**
  - Reads test cases until EOF; each test begins with $n$ ($1 \le n \le 100,000$) followed by $n$ integers.
  - Outputs dominant peaks in their original order.
- **Example:**
  - Input: `1 4 2 3 5` $\rightarrow$ Output: `5`
  - Input: `3 1 4 1 2 1` $\rightarrow$ Output: `4 2 1`
  - Input: `9 7 4 -2` $\rightarrow$ Output: `9 7 4 -2`

---

## Slide 12: Dual Algorithm Implementations
- **Golden Solution (`solution.cc`):**
  - **Complexity:** $O(n)$ linear time, $O(n)$ space.
  - **Algorithm:** Reads vector, scans right-to-left tracking running maximum, prints in forward order.
  - **Compliance:** Standard C++17 streams and vectors; zero forbidden STL.
- **Slow Solution (`solution-slow.cc`):**
  - **Complexity:** $O(n^2)$ quadratic worst-case.
  - **Algorithm:** For every peak, runs an inner loop scanning all subsequent elements.
  - **Early Exit:** Stops immediately when a peak $\ge$ current is found (satisfying constitution).

---

## Slide 13: Edge-Case Engineering & Vectorization Defeat
- **The Optimization Issue:**
  - Claude's initial naive solution was vectorized by `g++ -O2` (1.1s vs 0.34s, only a $3.2\times$ difference).
- **The Algorithmic Solution:**
  - Claude identified that strictly **decreasing** sequences force full quadratic scans ($O(n^2)$ comparisons).
- **Test Generation (`generate.ts`):**
  - Generates 2 strictly increasing and 3 strictly decreasing sequences of 100,000 elements.
  - Output reaches 3.1 MB; `generate.ts` automatically writes `private-efficiency-2-monotone.ops` with `--maxoutput=4`.

## Slide 22: Web Service Ingestion Protocol (`lib/upload.ts`)
- **Step 1: Filtering & Zipping:**
  - Excludes binaries (`.o`, `.exe`) and caches; bundles source into temporary zip archive.
- **Step 2: API Multipart Request:**
  - POSTs to `https://api.jutge.org/api` invoking `instructor.problems.create` with archive.
- **Step 3: WebStream Streaming:**
  - Opens `GET /api/webstreams/<id>` to stream real-time compiler, linter, and judge execution logs.
- **Step 4: Problem ID Assignment:**
  - Server emits `Problem P98421 created.` Client captures ID and writes `problem.yml`.

## Slide 26: Architectural Proposal: Phase 3 `@jutge/core`
- **The Core Problem:**
  - `jtk` currently mixes compiler execution, file I/O, terminal UI, and network calls.
- **The Proposed Solution:**
  - Extract all problem logic into a pure TypeScript headless SDK (`@jutge/core`) with zero terminal dependencies.
- **3-Layer Decoupled Architecture:**
  - **Layer 1: `@jutge/core` (Headless Engine):** Compilers, schemas, linting, packaging, and API client.
  - **Layer 2: `@jutge/cli` (`jtk v5`):** Thin CLI wrapper handling terminal arguments and progress bars.
  - **Layer 3: `@jutge/service`:** REST API & MCP server powering the Web Problem Editor and Claude Code.

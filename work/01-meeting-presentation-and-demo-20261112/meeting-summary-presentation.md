## Slide 3: Pedagogical Constitution & Problem Anatomy
- **Algorithmic Rigor (`spec/constitucio.md`):**
  - No wasted computation. Searches must terminate immediately on success.
  - Optimal solutions pass easily; naive solutions time out deterministically.
- **Restricted C++17 Subset:**
  - **Allowed:** `std::vector`, `string`, `queue`, `stack`, `algorithm`, standard I/O (`cin`/`cout`).
  - **Restricted `auto`:** Permitted only for iterators and clear return types.
  - **Forbidden:** No `std::unordered_map` (prevents hash attacks / unstable orders).
  - **Forbidden:** No lambdas, `enum class`, `constexpr`, `string_view`, `variant`, structured bindings, or exceptions.
- **Problem Directory (`.pbm`) Anatomy:**
  - `handler.yml`: Driver (`std`), compiler (`G++17`), source modifier (`none`).
  - `problem.en.tex`: LaTeX statement using standard Jutge macros (`\SampleTwoCol`).
  - `solution.cc`: Optimal reference solution.
  - `scores.yml`: Integer points summing to 10 (4 points correctness, 6 points efficiency).
  - `generate.ts`: TypeScript testcase generator for randomized edge cases.

## Slide 5: Problem Design: "Dominant Mountain Peaks"
- **Problem Concept:**
  - A mountain peak is dominant if strictly higher than all peaks appearing to its right.
- **Input / Output Specification:**
  - Reads test cases until EOF; each test begins with $n$ ($1 \le n \le 100,000$) followed by $n$ elevations.
  - Prints dominant peaks in their original order from left to right.
- **Sample Cases:**
  - Input: `1 4 2 3 5` $\rightarrow$ Output: `5`
  - Input: `3 1 4 1 2 1` $\rightarrow$ Output: `4 2 1`
  - Input: `9 7 4 -2` $\rightarrow$ Output: `9 7 4 -2`
- **Dual Implementations:**
  - **Golden (`solution.cc`):** $O(n)$ linear scan from right to left tracking running maximum.
  - **Slow (`solution-slow.cc`):** $O(n^2)$ search for each peak with early break at first higher peak.
- **Defeating Compiler Vectorization:**
  - Strictly decreasing sequences force full quadratic scans; `generate.ts` creates `.ops` for 3.1 MB output.

## Slide 9: Phase 3 Architecture Proposal: `@jutge/core`
- **Technical Debt in Existing `jtk`:**
  - `lib/maker.ts` (700+ lines) mixes compilers, file traversal, and terminal styling in one file.
  - Interactive prompts coupled with build logic prevent headless execution by web backends or AI agents.
- **Proposed Solution: 3-Layer Decoupled Architecture:**
  - **Layer 1: `@jutge/core` (Headless Engine):**
    - Pure TypeScript SDK for compiling, linting, packaging, and API communication with `--json` outputs.
  - **Layer 2: `@jutge/cli` (`jtk v5`):**
    - Thin CLI wrapper handling terminal arguments and progress spinners.
  - **Layer 3: `@jutge/service`:**
    - REST API & MCP (Model Context Protocol) server powering the Web Problem Editor and Claude Code.

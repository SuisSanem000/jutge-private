## 1. What Is a Jutge Problem?

Students submit autonomous source code to Jutge.org. The grading server compiles and runs the submission against a suite of input test cases (`*.inp`). If the student's output matches the expected output (`*.cor`) byte-for-byte and executes within the CPU time and memory limits, the submission passes.

### Standard Grading Verdicts
*   **`AC` (Accepted):** The program is completely correct and runs within efficiency bounds.
*   **`WA` (Wrong Answer):** Output does not match the expected `.cor` file.
*   **`EE` (Execution Error / Time Limit Exceeded):** The program crashed, ran out of memory, or timed out.
*   **`PE` (Presentation Error):** Output is logically correct but contains formatting whitespace or case errors.

## 2. Problem Types & Compiler Modes

The problem type is defined in `handler.yml` via the `compilers` and `source_modifier` keys:

### 1. `G++17` (Single C++ Source File)
The student submits a single `.cc` file.
*   **`source_modifier: none` (Whole Program):** The student submits a complete executable program with a `main()` function reading from standard input and writing to standard output.
*   **`source_modifier: no_main` (Single Function):** The student submits only a specific function or class. The test harness merges this with a teacher-provided `main.cc` before compilation.
*   **`source_modifier: structs` (Struct Function):** Similar to `no_main`, used when custom `struct` definitions are required.

### 2. `PRO2` (Single File Linked with Teacher Library)
The student submits a single `.cc` or `.hh` file that links with multiple teacher files:
*   **`public/` directory:** Files available for students to download to build and test locally (e.g. `main.cc`, `Makefile`, `.clang-format`, `.vscode/launch.json`).
*   **`private/` directory (optional):** Secret teacher test harnesses or solutions that overwrite `public/` files on the grading server during evaluation.

### 3. `MakePRO2` (Multi-File Archive)
The student submits a `.tar` archive containing multiple `.cc`, `.hh` files and a custom `Makefile`.

## 3. The `.pbm` Folder Anatomy

A problem directory must end in `.pbm`. A standard `PRO2` or `G++17` problem contains:

```
NN-problem-title.pbm/
├── handler.yml                  # Execution settings, compiler type, time limits
├── problem.yml                  # Server identity & passcode (generated by jtk upload)
├── problem.en.tex               # Formal problem statement in LaTeX
├── problem.en.yml               # Title, author, translator metadata
├── solution.cc                  # The Golden Solution (reference implementation)
├── solution-slow.cc             # Alternative slow solution (verifies time limits)
│
├── public/                      # [PRO2 only] Student downloadable bundle
│   ├── .clang-format            # Code formatting rules
│   ├── .vscode/                 # VS Code tasks.json and launch.json for students
│   ├── main.cc                  # Main test runner (if source_modifier is no_main)
│   └── Makefile                 # Build script
│
├── sample-1.inp                 # Public sample test case 1 (shown in statement)
├── sample-2.inp                 # Public sample test case 2 (shown in statement)
├── generate.ts                  # Testcase generator (TypeScript script with executable bit)
│
├── private-correctness-1.inp    # Private test: boundary & edge cases
├── private-correctness-2.inp    # Private test: small & medium inputs
├── private-efficiency-1.inp     # Private test: maximum constraint inputs
├── private-efficiency-2.inp     # Private test: worst-case performance inputs
│
├── scores.yml                   # Partial scoring rules by test prefix
└── <test>.ops                   # Optional limit overrides (e.g. --maxoutput=5MB)
```

> **Invariant on `.cor` files:** Expected output files (`*.cor`) are **never written by hand or an LLM**. They are generated automatically by running `jtk make` with the golden solution!

## 4. Problem Statement Anatomy (`problem.en.tex`)

Every LaTeX statement must follow this exact section structure:

1.  **Prerequisites / Conceptual Context:** Brief introduction explaining the real-world or mathematical context.
2.  **Problem Statement:** Detailed explanation of the task. If it is a function, include Doxygen comments with `@pre` (preconditions) and `@post` (postconditions).
3.  **Input Description:** Clear description of how input is formatted, bounds on sequence lengths, and data types.
4.  **Output Description:** Exact output format, ordering of elements, and tie-breaking rules.
5.  **Sample Input & Output Tables:** Clear samples that illustrate standard cases, edge cases, and empty input handling.

---

## 5. Testcase Generator (`generate.ts`)

Private test cases must be generated programmatically using a dedicated script:
*   Must use the shebang line: `#!/usr/bin/env bun`
*   Must have executable permissions (`chmod +x generate.ts`).
*   Must contain dedicated generator functions for each test category (e.g. `generateCorrectness()`, `generateEfficiency()`).
*   Must define constants for data sizes at the top rather than using magic numbers.

## 6. Pre-Flight Quality Checklist (For AI & Human Review)

Before approving any generated problem, verify:

1. [ ] **Pedagogical Constitution:** Solution uses only the allowed C++17 subset (no forbidden `unordered_map`, lambdas, etc.).
2. [ ] **Early Termination:** Searches and loops abort immediately once the result is determined.
3. [ ] **Strict Invariants:** Every `.inp` has a matching `.cor` produced by `jtk make`.
4. [ ] **Test Categorization:** Tests are divided into public samples, private correctness, and private efficiency.
5. [ ] **Slow Solution Contrast:** A slow/naive solution (`solution-slow.cc`) is verified to receive `EE, time-limit exceeded` on efficiency tests.
6. [ ] **Formatting:** All `.cc` and `.hh` files are cleanly formatted with `clang-format`.
7. [ ] **Clean Lint:** Running `jtk lint` produces 0 errors and 0 warnings.
